# DoOps 平台与集群资产可视化 · 功能设计

2026 年 11 月 19 日｜产品评审稿。适用对象为使用 DoOps Gateway 管理基础设施和应用的团队。下文的“新增”“完善”均为拟议改动，现状以当前工作区为依据。

## 1. 需求与范围

DoOps 应让平台管理员看到资产接入情况，让值班人员在集群内定位故障及其业务影响，让资产负责人从巡检报告核实整改结果。三个任务共用资产编号、关系和证据。

| 需求 | 产品要求 |
|---|---|
| 平台与集群两级看板 | 平台看板汇总当前 Gateway 下用户可见的资产；集群看板聚焦一个已登记的集群，支持按命名空间筛选。已登记但未归属集群的机器，在平台可见范围内单列。 |
| 资产拓扑与覆盖率 | 展示业务依赖、运行部署、物理承载三类有向关系，可从业务查资源，也可从资源反查业务。按盘点基线，分别验收在役服务器和业务系统的拓扑覆盖率，两项均须达到 80%。 |
| 资产监控 | 可查看机器、操作系统、内核、进程、应用程序、数据库六类对象，按适用范围提供 CPU、内存、GPU、网络流量、业务请求量和存储容量的现值、历史趋势和缺数说明。 |
| 巡检与报告 | 纳入计划的资产至少每周自动巡检一次，覆盖机器、漏洞与补丁、应用三类检查。每个应检周期有报告，可追踪漏检、整改及复检证据。 |

**范围约定。** 平台采用当前登录的 Gateway。集群采用台账内稳定的集群资产编号；本轮首个集群类型沿用产品已有的 K8s。一个集群可以有多个 Agent 来源，每个来源分别记录其可读范围。业务系统是盘点对象，可以包含多个应用；同一应用可以有多个部署实例。环境、项目、责任团队可作为通用筛选字段，缺少这些字段也能查看资产。 [现有资产接口与权限](../../backend/docs/DOOPS_API_GUIDE.md#资产台账)

## 2. 页面放在哪里

### 从一台 Linux 机器接入资产看板

机器台账用 `asset_id` 标识资产，可以先登记尚未接入的机器。执行目标用 `(cluster, instance)` 标识 Agent，Agent 从目标侧主动建立到 Gateway 的反向连接。集群看板按台账中的集群资产编号聚合，可关联多个 Agent 来源。机器 IP、Agent 路由、集群资产编号分别用于定位主机、授权执行和统计去重。[系统架构](../../README.md#architecture) · [Gateway 与 Agent 通道](../../backend/docs/DOOPS_GATEWAY_TUNNEL.md)

用户在 Web 控制台发起实时采集，Next.js 服务端将请求送至 Gateway。Gateway 校验登录用户对目标的授权，使用已建立的连接将任务交给目标 Agent 并记录审计。Agent 在实际有权观测的环境运行工具；返回的样本注明资产编号、来源目标、采样时间和单位。定时巡检由独立执行器按计划触发，使用其绑定账号走 Gateway。页面查询历史数据时也重新按当前授权筛选。[授权与凭据边界](../../AGENTS.md#canonical-architecture) · [周检执行器](../../backend/inspection/README.md)

在明确需要跨主机操作时，现有结构化 SSH 由选定的 Agent 发起：`--target` 指定已授权 Agent，`--host` 指定该 Agent 能到达的 SSH 主机。SSH 主机保留自己的资产编号和身份核验；该次操作沿用原 Agent 的目标授权与审计，CLI 支持 Agent 侧已配置的 OpenSSH 身份。仅有主机密码时可按安装流程自举，资产页面接入时匹配已注册的 Agent。[结构化 SSH 的执行语义](../../backend/docs/DOOPS_USAGE_GUIDE.md#exec)

## 3. 看板上的数字与关系怎么计算

**覆盖率。** 管理员在看板点击“覆盖率明细”选择基线版本和统计日，查看两张对账表并导出缺口。机器和业务系统沿用各自的台账维护入口。盘点基线应包含应纳管而尚未被 Agent 发现的资产。

| 指标 | 分母 | 计入分子的条件 |
|---|---|---|
| 在役服务器拓扑覆盖率 | 本范围基线中的在役服务器，按稳定编号去重。基线明确物理机和 VM 的统计范围。 | 能从拓扑定位到该编号，且有一条已核验的运行或承载关系。 |
| 在役业务系统拓扑覆盖率 | 本范围基线中的在役业务系统，按系统编号去重。 | 能定位到系统，且至少有一条已核验的部署实例或托管服务关系。 |

正式验收取统计日截止时已经核验、且当时仍有效的关系，保存基线版本、截止时间、分子与分母明细。周五补录的关系进入周五及以后的快照。历史纠错产生新修订并保留原快照、修订原因和操作者。

平台独立去重计算。跨两个集群的业务系统在各自范围内可见，在平台分子、分母各计一次。集群分母只包含基线中明确归属该集群的资产，待归属项在平台列出。未导入基线显示“待建立基线”，分母为零显示“无适用资产”。只有获得完整基线范围的用户才能查看正式验收结果，其余用户查看明确标注的“我的可见范围”。拓扑覆盖率、有效指标覆盖率、本周巡检完成率分别展示；离线资产沿用盘点时的在役状态。

**拓扑关系。** 业务系统包含应用；应用部署实例运行于工作负载或机器、使用数据库；工作负载调度至 Node，Node 可映射到机器，VM 由物理机承载。操作系统、内核和进程从机器展开。每条关系保留方向、来源和核验时间。可用来源为已观测的部署元数据、已有台账映射和人工确认。名称相似、IP 相同或同处命名空间都不足以自动判定业务依赖。两个来源看到同一对象时按稳定标识去重；证据冲突时展示待确认。

**指标语义。** 两级看板共用时间范围和单位。CPU、内存等比率按各对象实际容量加权，汇总旁展示有样本对象数；物理机容量与其 VM 分配量分别查看。跨业务汇总请求量须选择单一计量层，防止同一请求在入口和应用各计一次。

| 对象或指标 | 详情页要回答的问题 |
|---|---|
| 机器、操作系统、内核、进程 | 机器是否运行、何时重启，OS 与当前运行内核是什么版本，是否有 OOM，哪个进程占用 CPU 或常驻内存。进程以机器、启动周期和进程启动时间辅助识别，避免 PID 复用。 |
| 应用程序、数据库 | 哪个部署版本受影响，请求量、时延、错误率何时变化；数据库是否可用、连接及存储是否异常、哪些应用依赖它。查询量与业务请求量分别计量。 |
| GPU、网络流量、存储容量 | GPU 利用率及显存按设备展示；网卡收发按字节每秒，业务请求按次数或请求每秒；存储分别呈现总量、已用和可用。无 GPU 显示“不适用”，有 GPU 缺样本显示“缺数据”。 |

## 4. 巡检功能与每周报告

创建计划时选择资产范围、检查项、责任人、时区和执行时间。保存前预览应检对象、所需数据和未满足条件。每个周期冻结应检清单；未接入、离线或缺少必要证据的资产计入本期缺口。已有单目标工具继续用于即时诊断，计划与报告需新增独立的持久记录。

| 分组 | 检查项 | 结果需要包含的证据 |
|---|---|---|
| 机器 | 运行与重启、CPU 与内存、可疑进程、配置合规、异常登录与权限变更 | 目标资产、窗口、指标样本或命中规则、脱敏事件摘要；宿主数据不可读时标明受限范围。 |
| 漏洞与补丁 | 应用组件的已知漏洞、待更新补丁、修复验证 | 实际部署版本或镜像摘要、适用公告、修复版本。复检比较同一资产与问题的前后证据，区分已修复、仍受影响、无法验证。 |
| 应用 | 服务可用性、数据库状态、流量异常、Web 安全配置、指定 API | 服务或接口标识、采样时间、状态、时延和预期结果；保留测试窗口，只展示必要的脱敏信息。 |

计划详情分别显示责任人和绑定的 Gateway 执行账号。建议由管理员指定已有受管执行账号，按目标授予权限。每次首跑、重试及补跑都按同一执行账号检查 `cluster/instance` 授权，执行服务只负责触发与收集结果。责任人变更不自动转移执行身份，执行账号变更须留审计记录。

计划建议由独立的巡检执行服务按周触发，经 Gateway 使用已授权目标和 Agent 执行，日志关联同一运行编号。计划执行前复核执行身份与当前授权，撤权后的目标记录为未执行。周期、资产及检查项共同标识一条应检结果，重复触发复用该结果。重试和超时以策略上限结束；逾期记为漏检，补跑关联原周期并保留实际时间。每期报告列出应检、实检、发现、证据不足、漏检、负责人及复检结果；整期无可用目标也产生带原因的报告。持续异常告警与每周报告均可定位同一资产。[Gateway 职责与授权约定](../../AGENTS.md#canonical-architecture)

| 身份、台账、关系 | 当前 Gateway 身份和目标授权；现有机器、集群来源、命名空间、Node 关联及盘点导入能力 | 增加业务系统、应用、数据库稳定标识、关系证据和盘点基线。服务端按当前身份计算看板、覆盖率及缺口。资产关系仅当两端均可见才返回。 |
| 观测与历史 | 已授权 Agent、K8s、DoSql、网站检查等对应来源 | 为指标样本关联资产编号、时间、单位、来源和质量。历史曲线需要留存真实样本，平台显示有数据的资产比例。指标查询、拓扑查询和报告下载使用同一可见范围。 |
| 巡检与报告 | Gateway 目标执行授权、受管凭据引用和审计 | 持久化计划、周期快照、执行尝试、报告、发现与复检证据。服务端验证报告完整性，报告详情与导出均复核访问范围；混合权限报告仅呈现当前可见明细及对应汇总。 |

多来源集群先按授权过滤来源和对应证据，再计算图节点、指标、覆盖率和导出结果。即使用户能看到关系两端，只由未授权来源提供的关系仍不可见。管理员可核对有权管理的基线及未接入台账。

初次无资产时，管理员可直接“导入机器”或“从 Agent 发现集群”；普通用户看到授权与接入状态。来源掉线后仍显示带时间的最后观测，实时诊断标明不可用。指标已过期时曲线保留断点；权限收回后重新查询，清除上一范围的详情、图节点与统计。直接打开历史链接时同样验证权限。小屏使用可逐级展开的关系列表，支持与图中相同的查看依赖和反查影响动作。

## 6. 建设顺序与功能验收

| 阶段 | 首次可交付的页面和用户行为 | 关键验收场景 |
|---|---|---|
| 一 · 资产与拓扑 | 平台看板、集群详情、业务系统台账、资产关系、覆盖率缺口。 | 两个 Agent 对应同一集群，平台显示一个集群和两个来源。两个应用共用同一数据库，反向查询列出两个应用。登记但未入集群的机器可从平台找到。100 台服务器覆盖 85 台、50 个系统覆盖 38 个时，两项分别为 85% 和 76%，系统仍差 2 个。 |
| 二 · 监控定位 | 六类资产详情、六类指标、监控趋势与异常入口。 | 从集群内存异常进入机器及高占用进程，再查关联应用。网络吞吐上升但请求量稳定时两条曲线如实显示。GPU 采集失败与无设备分别展示，双来源采集的同一机器只计一次。 |
| 三 · 巡检与报告 | 每周计划、周期执行、报告导出、整改复检、审计下钻。 | 验证一次正常自动执行和一次中断周期。离线或撤权均留下缺口，重复触发不增加应检数。整改后核对已部署版本，报告保留前后证据。无权用户从深链、图谱和导出均无法获得受限资产。 |

### 正式环境验收证据

- **拓扑与盘点。** 留存基线版本、关系有效期、授权范围、分子分母及逐项明细。两项 80% 的正式结果都要能从明细重新计算。
- **监控。** 用同一时间窗对照采集源、接口计数器、设备及数据库观测。验证数据延迟、断流、无设备和恢复；验证撤权后深链与导出的访问结果。
- **自动周检。** 在指定时区记录实际调度开始、截止、报告生成和下一次计划时间。中断一次执行，再验证重复调度和补跑；将检查项、执行账号、目标、审计编号和报告关联起来。
- **报告与整改。** 用可控测试版本演练“仍受影响、已修复、证据不足”。报告保留整改前后两次证据，并核对不同身份的下载内容。原始凭据、原始登录日志和完整请求体均不作为用户报告字段。
